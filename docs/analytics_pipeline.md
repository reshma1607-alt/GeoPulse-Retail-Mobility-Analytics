# GeoPulse Analytics Pipeline

## 1. Overview

GeoPulse is a hyper-local retail mobility analytics system designed to study movement patterns around retail locations.

The project uses synthetic anonymized GPS mobility data to simulate how mobile devices move through a city and interact with retail store catchment areas.

The analytics pipeline transforms raw GPS observations into useful retail mobility metrics such as store footfall, hourly traffic, visitor overlap, and potential cannibalization indicators.

The current pipeline is implemented using Python and Pandas. It is designed as the foundation for the later geospatial architecture involving Snowflake, Apache Sedona, PySpark, dbt, Kepler.gl, and React.

## 3. Input Data

The main input dataset is synthetic GPS mobility data.

The dataset contains the following fields:

| Field | Description |
|---|---|
| DeviceID | Anonymized identifier for a simulated mobile device |
| Latitude | Geographic latitude of the observation |
| Longitude | Geographic longitude of the observation |
| Timestamp | Date and time of the GPS observation |

The current development dataset contains:

- 1,000 simulated devices
- 50 observations per device
- 50,000 total GPS observations

---

## 4. Store Data

The pipeline also uses a store-location dataset.

| Field | Description |
|---|---|
| StoreID | Unique identifier for the store |
| StoreName | Name assigned to the simulated store |
| Latitude | Geographic latitude of the store |
| Longitude | Geographic longitude of the store |

The current development dataset contains five simulated retail stores.

---

## 5. Data Generation

The GPS data-generation module creates synthetic mobility observations for the configured number of devices.

Each device receives a unique DeviceID. Initial device positions are generated around the selected city centre, and subsequent observations introduce movement around the previous position.

The generator also increases the probability of observations occurring near retail stores during selected peak periods.

The current configuration includes:

- Morning peak: 07:00-10:00
- Evening peak: 17:00-21:00

The generated raw GPS data is stored in:

`data/raw/gps_pings.csv`

---

## 6. Data Validation

Before performing analytics, the generated GPS dataset is validated.

The validation module checks:

- Required columns
- Total number of records
- Number of unique devices
- Missing values
- Latitude range
- Longitude range
- Timestamp validity
- Number of observations per device

This stage helps identify data-quality problems before the data enters the analytics pipeline.

The validation script is:

`src/validation/validate_gps.py`

---

## 7. Mobility Summary

The mobility summary provides an overall description of the GPS dataset.

The analysis calculates:

- Total GPS observations
- Unique devices
- Number of dates
- Minimum latitude
- Maximum latitude
- Minimum longitude
- Maximum longitude

This provides an initial understanding of the geographic and temporal coverage of the dataset.

The mobility summary is generated by:

`src/analytics/mobility_summary.py`

---

## 8. Time-Based Analysis

The Timestamp field is used to create additional time features such as:

- Date
- Hour
- Day

GPS observations are grouped by hour to understand how mobility changes throughout the day.

This hourly profile can later be used for time-series visualization and dashboard analysis.

---

## 9. Store Catchment Analysis

A store catchment area represents the geographic region surrounding a retail store.

GeoPulse currently uses a 500-meter catchment radius.

GPS observations within this radius are associated with the corresponding store's catchment area.

This provides the basis for calculating store-level footfall.

---

## 10. Geographic Distance Calculation

The store analysis uses the Haversine formula to calculate the approximate distance between geographic coordinates.

The calculated distance is expressed in meters and is compared with the 500-meter catchment threshold.

This allows GPS observations to be associated with stores based on geographic proximity.

---

## 11. Store Footfall Analysis

Store footfall analysis identifies GPS observations occurring within each store's catchment area.

For every store, the pipeline calculates:

- GPS observations
- Unique visitors
- Catchment radius

Unique visitors are calculated using DeviceID because a single device can generate multiple GPS observations.

The output file is:

`data/sample/store_footfall_summary.csv`

---

## 12. Hourly Footfall Analysis

Hourly footfall combines spatial and temporal information.

GPS observations within a store's catchment area are grouped by:

- Date
- Hour
- Store

The pipeline calculates:

- GPS observations
- Unique visitors

for each store and hour.

The output file is:

`data/sample/hourly_footfall.csv`

---

## 13. Device Store Visit Analysis

The device visit module identifies relationships between simulated devices and retail stores.

The resulting dataset contains:

- DeviceID
- Timestamp
- StoreID
- StoreName

This creates a device-to-store visit dataset that can be used to study visitor movement between different retail locations.

The output file is:

`data/sample/device_store_visits.csv`

---

## 14. Visitor Overlap Analysis

Visitor overlap measures the number of devices associated with multiple stores.

For every pair of stores, the pipeline calculates:

- Visitors at Store A
- Visitors at Store B
- Shared visitors
- Overlap percentage

Shared visitors are devices that occur in both store visitor sets.

The output file is:

`data/sample/visitor_overlap.csv`

---

## 15. Overlap Percentage

The current overlap percentage is calculated using shared visitors and the union of visitors from the two stores.

```text
Overlap Percentage =
Shared Visitors / Visitors in Union × 100
```

This provides a normalized measure of visitor overlap between two stores.

---

## 16. Cannibalization Analysis

Cannibalization analysis uses visitor overlap as a development-stage indicator.

For each store pair, the system calculates:

- Visitors at Store A
- Visitors at Store B
- Shared visitors
- Overlap percentage
- Cannibalization percentage
- Cannibalization indicator

The current development categories are:

```text
Below 25%       → Low
25% to <50%     → Medium
50% or higher   → High
```

These categories are analytical indicators and do not directly represent actual sales loss.

The output file is:

`data/sample/cannibalization_analysis.csv`

---

## 17. Peak Traffic Analysis

The peak traffic module groups observations into:

- Morning Peak: 06:00-11:00
- Midday: 11:00-17:00
- Evening Peak: 17:00-22:00
- Night: 22:00-06:00

For each period, the pipeline calculates:

- Total observations
- Unique devices

This helps identify the periods with higher mobility activity.

The output file is:

`data/sample/peak_traffic_summary.csv`

---

## 18. Store Performance Comparison

The store comparison module compares stores based on unique visitor activity.

The analysis calculates:

- Unique visitors
- Visitor share percentage
- Footfall rank

This provides a simple comparison of visitor activity associated with each simulated store.

The output file is:

`data/sample/store_performance.csv`

## 20. Python Modules

The current analytics pipeline is organized into separate Python modules.

### Data Generation

`src/data_generation/generate_gps.py`

Generates the synthetic GPS mobility dataset.

### Sample Creation

`src/data_generation/create_sample.py`

Creates a smaller sample dataset for development and demonstration.

### Data Validation

`src/validation/validate_gps.py`

Checks the quality and structure of the generated GPS data.

### Mobility Summary

`src/analytics/mobility_summary.py`

Provides overall and time-based mobility statistics.

### Store Footfall

`src/analytics/store_footfall.py`

Calculates store-level footfall using the catchment radius.

### Hourly Footfall

`src/analytics/hourly_footfall.py`

Calculates store activity by date and hour.

### Device Store Visits

`src/analytics/device_visits.py`

Identifies devices that enter individual store catchment areas.

### Visitor Overlap

`src/analytics/visitor_overlap.py`

Calculates shared visitors between store pairs.

### Cannibalization

`src/analytics/cannibalization.py`

Calculates development-stage cannibalization indicators.

### Peak Traffic

`src/analytics/peak_traffic.py`

Groups mobility observations into different traffic periods.

### Store Comparison

`src/analytics/store_comparison.py`

Compares stores using visitor activity and footfall rank.

### Pipeline Runner

`src/analytics/run_pipeline.py`

Provides a sequential way to execute the main analytics modules.

`data/raw/`

## 24. Planned Geospatial Architecture

The planned future architecture will extend the current Python implementation using the following technologies.

### Snowflake

Snowflake will provide the data-storage layer for large-scale mobility and geospatial data.

The planned implementation will make use of geographic data types and spatial capabilities.

### Apache Sedona / PySpark

Apache Sedona and PySpark will be used for distributed geospatial processing.

They will support spatial joins and catchment analysis when the project moves from the current development implementation to a distributed architecture.

### dbt

dbt will be used for data transformation and analytical modeling.

It will support the creation of structured models for metrics such as hourly footfall and visitor activity.

### Kepler.gl

Kepler.gl will be used for interactive geospatial visualization.

It can be used to visualize:

- GPS mobility
- Footfall
- Catchment areas
- H3 hexagons
- Movement patterns

### React

React will provide the dashboard interface and integrate the geospatial visualization components into an interactive application.

## 26. Current Limitations

The current system uses synthetic GPS data for development.

The generated locations do not represent real people or real customer movements.

The current catchment analysis uses a circular 500-meter radius rather than actual commercial zoning polygons.

The current implementation is designed for development and testing and does not yet represent the complete distributed geospatial architecture.

The current cannibalization metric is based on visitor overlap and should be treated as a development-stage indicator rather than a direct measurement of sales cannibalization.
